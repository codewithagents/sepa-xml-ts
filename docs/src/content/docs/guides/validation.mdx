`sepa-xml-ts` provides two layers of validation that can be used independently or together.

## Layer 1: business-rule validation

Business validation runs against the Zod schema, which is the single source of truth for the
model. It enforces all semantic constraints:

- IBAN mod-97 checksum
- BIC format (when provided)
- SEPA charset EPC217-08: basic Latin by default; the extended set in text fields only with
  `{ charset: 'extended' }`; identifiers, references and codes basic Latin in every mode (see
  [Character set](#character-set-epc217-08))
- Amount constraints: max 2 decimal places, and the EPC AT-06 range of 0.01 to 999,999,999.99 EUR per transaction
- Identifier slash rules: MsgId, PmtInfId, and EndToEndId must not start or end with `/` and must not contain `//`
- Date format `YYYY-MM-DD` for execution and collection dates
- SEPA Creditor Identifier check digits (ISO 7064 MOD 97-10, strict), with German `DE` identifiers required to be exactly 18 characters

These refinements live on the Zod schema, so they apply to every entry point: `validate*`, the
writers (which validate before emitting), and `parse` (which validates what it reads). The amount
cap and identifier rules are derived from the EPC implementation guidelines, not copied from any
third-party library.

### `validateCreditTransfer(input, options?)`

Validates any unknown input as a `CreditTransferDocument`. Returns a typed result.
Accepts an optional `{ profile }` option to run bank-profile checks on top of the base Zod rules,
and an optional `{ charset }` option (default `'basic'`).

```typescript
import { validateCreditTransfer, requireBic } from 'sepa-xml-ts'

const result = validateCreditTransfer(doc)

if (!result.ok) {
  // result.errors: ZodIssue[]
  for (const err of result.errors) {
    console.error(err.path.join('.'), err.message)
  }
} else {
  // result.data: CreditTransferDocument (validated)
  const xml = writeCreditTransfer(result.data)
}

// With a bank profile:
const profileResult = validateCreditTransfer(doc, { profile: requireBic })

if (!profileResult.ok) {
  // result.errors: ZodIssue[] (base schema failures)
  // result.profileIssues: ProfileIssue[] (bank-profile failures)
  console.error(profileResult.errors, profileResult.profileIssues)
}
```

### `validateDirectDebit(input, options?)`

Same for `DirectDebitDocument`.

```typescript
import { validateDirectDebit, requireBic } from 'sepa-xml-ts'

const result = validateDirectDebit(doc, { profile: requireBic })
```

## Result shape

Both validate functions return a `ValidationResult`:

```typescript
type ValidationResult<T> =
  { ok: true; data: T } | { ok: false; errors: ZodIssue[]; profileIssues?: ProfileIssue[] }
```

`profileIssues` is only present when a profile was supplied.

## Writers validate implicitly

`writeCreditTransfer` and `writeDirectDebit` run the same validation internally. If the model
fails, they throw an `Error` whose message lists the same issues as `path: message`. You do not
have to call `validateCreditTransfer` separately before writing unless you want the typed result
shape.

## Character set (EPC217-08)

SEPA defines a basic Latin set every bank accepts: `a-z A-Z 0-9 space / - ? : ( ) . , ' +`.
EPC217-08 extends it with the local-language and special characters of its official conversion
table (for example `č š ž ä ö ü ß`, Greek and Cyrillic letters, `€ & @`), which banks may accept
by prior agreement.

| Function                                        | Default `charset` |
| ----------------------------------------------- | ----------------- |
| `writeCreditTransfer`, `writeDirectDebit`       | `'basic'`         |
| `validateCreditTransfer`, `validateDirectDebit` | `'basic'`         |
| `parse`                                         | `'extended'`      |

`parse` defaults to `'extended'` because EPC217-08 asks a receiver to process text as received
and to reject only characters outside the conversion table. Use `parse(xml, { charset: 'basic' })`
for the strict check. A parsed document with extended text needs `{ charset: 'extended' }` to be
written again.

The option applies to human-readable **text fields** only (EPC217-08 section 6.3):

- **Text fields follow the option:** party names, postal address fields (except `country`), and
  unstructured remittance information (`remittanceInfo`).
- **Basic Latin in every mode:** `messageId`, batch `id`, `endToEndId`, the mandate id, purpose and
  category-purpose codes (including `proprietary`), structured party identifications, and every
  field of a structured remittance.

A value outside the set fails with a message that names each character and its code point:

```text
creditor.name: Value contains characters outside the SEPA charset (EPC217-08): "Š" (U+0160).
By default only the basic Latin set is allowed (a-z A-Z 0-9 space / - ? : ( ) . , ' +). If your
bank accepts the EPC217-08 extended character set, pass { charset: 'extended' }
(SepaCharset.Extended). Otherwise convert the value with toSepaCharset(value).
```

```typescript
import { writeDirectDebit, toSepaCharset, SepaCharset } from 'sepa-xml-ts'

// Your bank accepts the extended set:
const xml = writeDirectDebit(doc, { charset: SepaCharset.Extended })

// Otherwise convert text fields with the official EPC conversion table:
toSepaCharset('Maja Štupica') // 'Maja Stupica'
toSepaCharset('Müller & Söhne') // 'Muller + Sohne'
toSepaCharset('Maja Štupica 🎉', { charset: 'extended' }) // 'Maja Štupica .'
```

`toSepaCharset` normalizes to NFC, applies the section 6.2 sender rules (`&` to `+`, `@` to
`(at)`, `€` to `E`, `_` to `-`), then the table's basic conversion, and uses a full stop for
anything without a conversion (emoji, other scripts, typographic quotes such as `’`). It never
drops, trims or truncates, so the result can exceed a field's maximum length. It converts one to
one (`ä` to `a`, `ß` to `s`); apply the German `ae`/`oe`/`ue`/`ss` convention yourself before
calling it if you need it. The no-break space (U+00A0) becomes a plain space for both targets:
text fields do not accept it in either charset, because the table converts it to a space and it
would not survive a round trip.

<Aside type="caution">
  The German DK variants (`pain.001.003.03`, `pain.008.003.02`) throw on `{ charset: 'extended' }`:
  the DK formats define their own character rules (DFU-Abkommen Anlage 3), which this library does
  not ship.
</Aside>

The writers return a string with an `encoding="UTF-8"` declaration and write extended characters
as they are (only `& < > " '` are escaped). Save files as UTF-8, and decode received files as
UTF-8 before calling `parse`. `parse` accepts only well-formed XML 1.0 with namespaces and
without a DTD: it decodes numeric character references such as `&#352;` and the five predefined
entities, and returns `ok: false` for a bare `&`, an undefined entity such as `&nbsp;`, a
reference to an illegal character, a mismatched end tag, `<![` outside a CDATA section, content
outside the root element, or a processing instruction with a quote still open at its `?>`.

## Layer 2: XSD validation (optional)

XSD validation checks the serialized XML against the official EPC ISO 20022 schema using
`libxml2-wasm`. It is an opt-in extra that lives behind the `sepa-xml-ts/xsd` subpath.

```typescript
import { validateXsd } from 'sepa-xml-ts/xsd'

const xsdResult = await validateXsd(xml)

if (!xsdResult.valid) {
  for (const err of xsdResult.errors) {
    console.error(err)
  }
}
```

`validateXsd` reads the message type and namespace from the root `<Document>` element and
selects the correct XSD. It covers all seven schemas:

- `pain.001.001.09`
- `pain.001.003.03` (German DK)
- `pain.001.001.03`
- `pain.008.001.08`
- `pain.008.003.02` (German DK)
- `pain.008.001.02`

<Aside type="tip">
  XSD validation loads `libxml2-wasm`, a native-compiled WASM module. It is intentionally kept
  behind a separate entry point so that write-only users never download the WASM blob. Only import
  `sepa-xml-ts/xsd` when you need it.
</Aside>

## When to use XSD validation

You generally do not need XSD validation in production write paths. The library already enforces
every constraint via the Zod schema and the writer. XSD validation is most useful for:

- Verifying files produced by a third party before processing
- Belt-and-suspenders CI checks after generating files
- Debugging: when the XSD rejects a file, the error message points at the exact element

## Testing strategy

The library's own CI uses XSD validation as an oracle in property tests: for every build, it
generates hundreds of random valid models, writes them to XML, and asserts each file passes the
official EPC XSD. This is what "XSD-as-oracle" means in the documentation.
